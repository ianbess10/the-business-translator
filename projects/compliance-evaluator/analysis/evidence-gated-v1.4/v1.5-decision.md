# Evidence-Gated Decision Pipeline v1.5 — Decision Record

## Decision

**Proceed later with a separately versioned v1.5 implementation that introduces a human-approved obligation-to-control coverage and evidence rulebook. Replace model-authored mapping completeness with deterministic coverage calculation and reduce the evidence model to bounded fact extraction. Do not modify, tune, rerun or rescore v1.4.**

This record selects architecture and release controls only. It does not create the rulebook, implement a v1.5 workflow, change the frozen dataset or labels, call a provider, execute regression cases, score results or prepare a holdout.

## Why a new version is warranted

v1.4 solved the v1.3 execution failure: all 24 cases completed, all 32 stage responses passed transport and semantic validation, `CON-007` completed, and no case was quarantined or retried.

The remaining three errors are not random. All three begin with incorrect model-authored mapping completeness. The current mapping stage receives:

- a human-approved atomic obligation;
- submitted control IDs;
- brief catalogue names and control types; and
- a list of other relevant controls.

It does not receive a reviewed statement of which obligation elements each control covers. The model must infer coverage from names. In two cases it overstated `C-CON-006`; in one it understated `C-CON-007`.

Further prompt engineering would make the model sound more deliberate without creating the missing authority. The next version must place approved business meaning in data and policy.

## Selected v1.5 architecture

### 1. Approved Coverage and Evidence Rulebook

Create a separately versioned, human-reviewed rulebook linked to each approved obligation. It must contain:

**Obligation elements**

- stable element ID;
- source-supported element statement;
- element type, such as establishment, operation, maintenance, governance or reporting;
- mandatory or conditional status; and
- approval and provenance metadata.

**Control coverage assertions**

- obligation ID and element ID;
- control ID;
- coverage state: `covers`, `partially_covers`, `does_not_cover` or `not_assessed`;
- approved rationale;
- owner and reviewer roles;
- effective date and version; and
- human-review status.

**Evidence requirements**

- stable requirement ID;
- linked obligation element and, where applicable, control ID;
- requirement class: `design_attribute`, `operating_record` or `adverse_indicator`;
- expected artefact or attribute;
- absence or deficiency classification;
- assessment frequency or period where relevant;
- evidence owner role; and
- approval and provenance metadata.

The rulebook is controlled business data, not a benchmark answer key. It must not contain case IDs, expected labels, evidence instance IDs, benchmark-specific wording or case-targeted exceptions.

### 2. Deterministic mapping completeness

For an entered assurance case, the runner will:

1. validate submitted control IDs against the catalogue;
2. load approved coverage assertions for the approved obligation;
3. union the obligation elements covered by the submitted current controls;
4. compare that set with all mandatory obligation elements; and
5. derive `complete`, `partial` or `no_suitable_control` deterministically.

Additional catalogue controls may be identified from the same rulebook as remediation candidates, but cannot change current membership.

If an element or submitted control lacks an approved coverage assertion, mapping is `not_assessable` and the case is quarantined for human review. The workflow must not infer missing authority from a control name.

This removes the model mapping call. The model remains an enabler for bounded evidence interpretation; the approved operating decision is a rulebook calculation.

### 3. Evidence model becomes fact extraction

The evidence stage will no longer author the final evidence assessment directly. For each applicable approved evidence requirement, it will return a bounded observed state:

- `present_complete`;
- `present_deficient`;
- `missing`;
- `adverse_indicator_present`; or
- `not_assessable`.

Each observation must reference an allowed requirement ID and supplied evidence ID, or explicitly record that no evidence item supports the requirement. Deterministic validation will reject unknown IDs, duplicate observations, evidence reuse that violates the rulebook and incomplete requirement coverage.

The prompt may interpret supplied descriptions, but it cannot create a new requirement, change mapping, decide severity, route remediation, decide escalation or conclude compliance.

### 4. Deterministic assurance derivation

Policy will derive the canonical evidence assessment from requirement class and observed state:

- missing or deficient `design_attribute` → `design_deficiency`;
- missing `operating_record` without adverse evidence → `missing_operating_evidence`;
- present adverse indicator → `adverse_operating_evidence`;
- all required items present and complete → `sufficient`; and
- unresolved required observations → `insufficient_to_assess` or quarantine according to the approved rule.

Mapping precedence remains explicit:

1. `design_deficiency` may establish the high design-gap outcome;
2. otherwise deterministic partial coverage takes precedence;
3. otherwise the derived evidence assessment applies.

Severity, remediation, owner routing and escalation remain deterministic.

### 5. Preserve execution evidence and quarantine

v1.5 retains the v1.4 append-only stage ledger, active case/stage marker, zero-retry rule and complete-or-quarantined terminal record.

Missing rulebook authority, invalid observation references, provider refusal, transport failure or semantic failure must quarantine the case without a policy conclusion. The same one-time batch continues. Quarantine remains an end-to-end error and release blocker.

## Expected execution shape

If implemented as selected, the future regression will use at most:

- 16 source/support model calls for cases without an approved obligation;
- zero model mapping calls;
- eight bounded evidence-observation calls for entered assurance cases; and
- **24 model calls in total**.

The reduction from 32 calls is not itself a release claim. It follows from moving an authority decision out of model inference and into approved data plus deterministic calculation.

## Generality and anti-overfitting controls

Because the rulebook is selected after observing regression failures, its independence must be protected explicitly:

- author from the approved obligation, source locator and control design documentation—not evaluator labels;
- prohibit benchmark case IDs, titles, evidence IDs, expected outcomes and error tags;
- require stable element and requirement IDs that are meaningful outside the dataset;
- require human review before the rulebook enters workflow tests;
- test unused combinations of obligation elements, controls and evidence states offline;
- maintain a static case-identity scan over rulebook and runtime artefacts; and
- freeze the rulebook before any v1.5 regression execution.

The existing 24 cases remain regression evidence and cannot validate whether the rulebook generalises. Independent validation remains a later, separately frozen stage.

## Controls retained without relaxation

v1.5 will retain:

- approved-obligation authority and source-stage bypass;
- source support separated from legal readiness;
- current controls separated from remediation candidates;
- catalogue owner resolution;
- mapping isolated from presented evidence and escalation proposals;
- evidence unable to change mapping membership;
- provider-subset schema audit and exact changed-contract certification;
- deterministic applicability, assurance and escalation policy;
- append-only stage evidence before validation;
- zero retry, repair, fallback and manual correction;
- mandatory human review and `not_determined` compliance conclusion;
- runner isolation from evaluator labels;
- quarantine-aware end-to-end evaluation;
- all 15 v1.4 release gates; and
- no holdout unless every regression gate passes.

## Required offline tests before certification and freeze

The future implementation must prove:

1. every approved obligation has a complete, human-reviewed element register;
2. every relevant control has explicit coverage assertions for each mandatory element;
3. current mapping completeness is derived without a model and without evidence input;
4. additional controls remain candidates and cannot complete current membership;
5. absent coverage authority quarantines rather than infers;
6. every evidence requirement is typed and linked to an obligation element;
7. design-attribute deficiency is distinct from missing operating evidence;
8. evidence observations reference only supplied evidence and approved requirement IDs;
9. all evidence states derive the expected canonical assessment and policy outcome;
10. partial-coverage precedence and design-deficiency precedence remain exact;
11. all 24 frozen paths terminate offline without runner access to labels;
12. a quarantine continues the batch with zero retry and blocks release;
13. the evaluator self-test remains exact and denominator disclosures remain correct; and
14. case-identity scanning finds no benchmark-specific rulebook or runtime content.

## Provider certification decision

The source/support contract may inherit v1.3 certification only if schema, prompt, request wrapper, model and endpoint hashes remain exact.

The mapping model contract is removed and requires no provider certification. Its replacement deterministic calculator requires offline boundary and rulebook-integrity tests.

The changed evidence-observation contract must receive one generic non-benchmark provider certification before freeze. Certification proves transport compatibility only, not mapping or evidence quality.

## Prohibited responses

v1.5 must not:

- modify, rerun or rescore v1.4;
- tune a prompt to the three failed case IDs or wording;
- copy evaluator labels into the rulebook;
- encode case-specific coverage or evidence exceptions;
- let the model invent obligation elements, coverage assertions or evidence requirements;
- infer coverage when approved authority is absent;
- allow evidence observations to alter mapping membership;
- retry, repair or normalize an invalid provider response;
- hide quarantine from end-to-end accuracy or release gates;
- change the model, endpoint or output mode after freeze; or
- proceed to holdout after any failed regression gate.
