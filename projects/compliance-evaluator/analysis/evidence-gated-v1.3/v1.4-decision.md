# Evidence-Gated Decision Pipeline v1.4 — Decision Record

## Decision

**Proceed later with a targeted, separately versioned v1.4 implementation that replaces redundant evidence outputs with one canonical model decision and adds stage-level execution evidence plus case quarantine. Do not modify, tune, rerun or score v1.3.**

This record selects the next architecture and release controls. It does not implement v1.4, create a v1.4 workflow, alter prompts or schemas, call the provider, execute regression cases, score any result or author a holdout.

## Why a new version is warranted

v1.3 corrected the provider contract and proved that all three exact schemas were accepted. Its sole regression nevertheless stopped on `CON-007` because the model expressed the design-deficiency decision inconsistently across `evidence_assessment` and `design_deficiency_evidence_present`.

The deterministic validator correctly blocked the contradiction. The next correction is not to weaken the validator or retry the model. It is to stop asking the model for multiple representations of one business fact.

The frozen assurance policy already maps `evidence_assessment` to assurance outcome, gap type, severity and remediation. The separate deficiency flags duplicate that classification, and `severity_recommendation` is not used by policy composition. Removing redundant model-authored fields reduces the semantic state space without reducing the operational control.

## Selected v1.4 architecture

### 1. Canonical evidence classification

The evidence stage will make `evidence_assessment` the sole model-authored classification, retaining its existing controlled enum:

- `sufficient`;
- `missing_operating_evidence`;
- `design_deficiency`;
- `adverse_operating_evidence`;
- `insufficient_to_assess`; and
- `not_assessed_no_current_control`.

The model will no longer separately author:

- `design_deficiency_evidence_present`;
- `adverse_indicator_present`; or
- `severity_recommendation`.

The transport contract will retain `case_id` and `rationale`. Deterministic validation will still enforce case identity, non-empty rationale and compatibility with mapping state.

### 2. Deterministic operational derivation

The existing frozen assurance policy remains authoritative for deriving:

- design-deficiency and adverse-indicator flags where audit traces require them;
- assurance outcome;
- gap type;
- gap severity;
- remediation action type; and
- escalation through the separate escalation policy.

Partial mapping precedence remains deterministic: an explicit canonical `design_deficiency` assessment may override partial-coverage treatment; otherwise partial coverage takes precedence. No model-authored severity or escalation proposal may override policy.

This is normalization, not automatic correction. The system derives one operational representation from one accepted classification rather than choosing between conflicting model fields.

### 3. Stage-level append-only execution evidence

Before semantic validation or downstream processing, the runner must persist an append-only stage record containing:

- run ID, case ID, execution position and stage;
- request ordinal and timestamp;
- provider response ID, model and finish reason;
- raw parsed response or an integrity-preserving representation sufficient for forensic review;
- transport-validation result;
- semantic-validation result and exact error;
- composition status; and
- retry count, fixed at zero.

The batch run state must record the active case and stage before each request. This removes the need to infer the failed identity from counters and ensures a rejected response remains auditable.

Sensitive-data handling must be considered before this pattern is used outside synthetic evaluation. Production logging would require minimisation, access control and retention policy.

### 4. Case quarantine without retry

A provider refusal, transport failure or semantic failure for one case will:

1. preserve the failed stage evidence;
2. mark that case `quarantined` with a controlled failure reason;
3. prohibit policy composition and operational conclusions for that case;
4. route it to mandatory human review;
5. make no retry, repair or substitute provider call; and
6. continue to the next frozen case within the same sole batch execution.

Continuing the batch is not a rerun of the failed case. It prevents one malformed case from concealing the behaviour of the remaining cases while remaining fail-closed at the case level.

### 5. Quarantine-aware evaluation

The evaluator will require one terminal record for every frozen case: either a completed prediction or a quarantined failure. It must:

- count each quarantined case as not end-to-end exact;
- report quarantine count and reasons separately from decision-field mismatches;
- fail the release decision if any quarantine exists;
- never synthesize missing decision fields for a quarantined case; and
- retain escalation metrics only for cases with actual completed predictions, with the reduced denominator disclosed.

This permits one complete measurement record without treating technical failures as valid predictions or allowing them to disappear from the headline result.

## Controls retained

v1.4 will retain without relaxation:

- the provider-compatible schema allowlist and recursive audit;
- one non-benchmark provider certification for every exact changed schema before freeze;
- certification/model/endpoint hash gates;
- separate source/support, mapping and evidence stages;
- approved-obligation source-stage bypass;
- mapping and evidence payload isolation;
- deterministic source, applicability, assurance, ownership and escalation policies;
- human review and `not_determined` compliance conclusion;
- evaluator-label isolation;
- no retry, automatic repair, mock, JSON-mode, model or endpoint fallback;
- one frozen regression execution and one evaluation invocation; and
- no tuning or rerunning after observation.

The frozen dataset, labels and `gpt-4o-mini-2024-07-18` snapshot remain unchanged for a future separately authorised regression.

## Required offline tests before certification and freeze

The future implementation must prove:

1. the new evidence transport schema contains no redundant classification fields;
2. every evidence-assessment enum deterministically produces the expected audit flags and assurance-policy outcome;
3. `CON-007`-shaped generic boundary fixtures distinguish missing operating evidence from design deficiency without using benchmark text or labels;
4. mapping precedence remains correct for complete, partial and no-current-control states;
5. every stage response is checkpointed before semantic validation;
6. missing, refused, transport-invalid and semantic-invalid stages produce one quarantined terminal case without a retry;
7. later cases continue after quarantine in the same batch;
8. the evaluator counts quarantines as non-exact and fails release while preserving metric denominators;
9. all 24 frozen input paths terminate offline as completed or quarantined without loading labels in the runner; and
10. certification hashes and zero-run gates remain mandatory.

## Provider certification decision

Only the evidence schema changes materially, so the future implementation must certify that exact evidence schema once using a generic non-benchmark sentinel input. The unchanged source and mapping schemas may rely on their preserved v1.3 certifications only if their schema, prompt, request wrapper, model and endpoint hashes remain identical and the v1.4 freeze manifest explicitly verifies that lineage. Any change requires a fresh non-benchmark certification for the affected contract.

Certification remains transport evidence, not model-quality evidence.

## Prohibited responses

v1.4 must not:

- modify, rerun or score v1.3;
- infer or reconstruct the unpreserved v1.3 response fields;
- repair or normalize a contradictory response after it is generated;
- retry a failed case;
- treat quarantine as a successful prediction;
- exclude quarantined cases from end-to-end exactness;
- weaken deterministic operational policies;
- expose labels to the runner;
- silently change the model, endpoint or output mode; or
- proceed to holdout if any regression release gate fails.
